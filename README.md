# HurmaStr — облік співробітників

HR-система на кшталт Hurma: довідник співробітників, оргструктура, відпустки та лікарняні.
Інтерфейс українською.

## Стек

Next.js 16 (App Router, Server Actions) · React 19 · TypeScript · Tailwind CSS v4 ·
Prisma 7 + SQLite · zod 4 · jose (JWT-сесії) · bcryptjs · nodemailer

## Запуск

```bash
npm install
npm run db:push     # створити таблиці
npm run db:seed     # типи відсутностей, довідники, акаунт адміністратора
npm run dev         # http://localhost:3000
```

Вхід за замовчуванням: **admin@hurma.local** / **admin12345**
(змінюється через `SEED_ADMIN_EMAIL` і `SEED_ADMIN_PASSWORD`).

Першим ділом відредагуйте картку «Адміністратор Системи» — впишіть свої дані.

## Змінні оточення (`.env`)

| Змінна | Призначення |
|---|---|
| `DATABASE_URL` | Шлях до SQLite, за замовчуванням `file:./dev.db` |
| `AUTH_SECRET` | Секрет для підпису сесій. **Обов'язково змініть на проді** |
| `APP_URL` | Базова адреса — використовується в посиланнях-запрошеннях |
| `SMTP_URL` | `smtp://user:pass@host:587`. Без неї запрошення не надсилаються поштою, а показуються посиланням для ручної передачі |
| `MAIL_FROM` | Відправник листів, напр. `HurmaStr <hr@company.com>` |

## Як влаштований облік днів

- **Відпустка** нараховується по **2 дні за кожен відпрацьований місяць** (24 дн./рік при повній ставці).
- **Лікарняний без довідки** — 2 дні на рік, **з довідкою** — 5 днів на рік.
- **Day Off** балансу не має — фіксується лише сам факт відсутності.
- Тривалість рахується в **робочих днях** (без субот і неділь). Державні свята не враховуються.
- Ставка (`workRate`) множить нарахування: 0.5 ставки → 1 день на місяць.

Джерело істини — журнал `LeaveLedgerEntry`. Таблиця `LeaveBalance` це лише кеш,
який повністю перебудовується з журналу (`syncBalances`), тому цифри не можуть розійтися.
Залишок ніде не зберігається, а обчислюється:

```
доступно = нараховано + перенесено + коригування − використано − на_погодженні
```

## Ролі

| Роль | Доступ |
|---|---|
| Адміністратор | Усе, включно з ролями й акаунтами |
| HR-менеджер | Кадрові картки, довідники, баланси, погодження |
| Керівник | Своя команда, погодження заявок підлеглих |
| Співробітник | Свій профіль, свої заявки, довідник, календар |

**Право погоджувати визначається структурно** — тим, що ви керівник заявника
(поле «Керівник» у картці) або керівник його відділу, — а не роллю в системі.
Керівник команди з роллю «Співробітник» усе одно бачить свою чергу погоджень.
Погодити власну заявку не може ніхто, включно з адміністратором.

## Життєвий цикл заявки

```
Чернетка → На погодженні → Погоджено ┐
                         ↘ Відхилено │
                                     └→ Скасовано (дні повертаються в баланс)
```

Маршрут будується автоматично з типу відсутності: керівник → HR, лише керівник, або лише HR.
Якщо погоджувача не існує (немає керівника і немає вільного HR), заявка **погоджується
автоматично** з явною позначкою — вона ніколи не «зависає» назавжди.

## Запрошення співробітників

1. Створіть картку і вкажіть **робочу пошту**.
2. На картці — блок «Доступ до системи»: оберіть роль і надішліть запрошення.
3. Співробітник переходить за посиланням, створює пароль і входить.

Посилання діє 7 днів. Повторне запрошення скидає старий пароль і завершує активні сесії.

## Календар і панель

- **Панель** — власний баланс, хто сьогодні відсутній, найближчі дні народження та річниці.
- **Календар** — місячна сітка з відсутностями (кольори й іконки типів),
  днями народження 🎁 та річницями роботи ⭐ (1 рік, 2 роки, 3 роки…).

Дні народження й річниці ніде не зберігаються окремо — вони обчислюються
з `birthDate` і `hireDate`, тож достатньо заповнити дати в картці.

## Корисні команди

```bash
npm run dev                              # режим розробки
```

## Структура

```
prisma/schema.prisma          модель даних
src/lib/                      дати, підписи, авторизація, права доступу
src/server/services/          бізнес-логіка: баланси, маршрути погодження, події
src/server/queries/           читання даних
src/server/actions/           серверні дії (мутації)
src/app/(auth)/               вхід і прийняття запрошення
src/app/(dashboard)/          основний інтерфейс
src/proxy.ts                  захист роутів (у Next 16 middleware зветься proxy)
docs/SPEC.md                  повна проєктна специфікація
```

## Перехід на PostgreSQL

У `prisma/schema.prisma` змініть `provider = "sqlite"` на `"postgresql"`,
поставте `@prisma/adapter-pg` замість `@prisma/adapter-better-sqlite3`
і оновіть створення адаптера в `src/lib/prisma.ts`. Поле `searchKey` тоді
можна прибрати на користь `ILIKE`.
